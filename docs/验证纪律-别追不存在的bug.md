# 验证纪律 —— 别追不存在的 bug

> 写这份东西的原因很直接：**本次会话里我为了一个不存在的问题烧掉了一个多小时。**
> 现场还原：测试套件报红说「日志里没有 `[bridge] 就绪`」，而同一时刻用另一种方式
> 读**同一个文件**，那行明明在里面。我判定它是 `bridge.rs` 的竞态，于是加逐次轮询
> 留痕 → 重新编译 → 重新打包 → 重跑，一路追下去。最后三次完全隔离的干净运行证明：
> **产品行为 3/3 稳定，那行一次就写成、立刻可读。**
> 真正的根因是**我自己测试环境的两处缺陷**（见下）。
>
> 所以这份文件的名字不叫"测试技巧"，叫**纪律**。

---

## 规则 1：先怀疑测试，再怀疑产品 —— 但要用**可判定的判据**，不能靠感觉

出现自相矛盾的现场时（"断言说没有，可我明明读到了"），第一件事不是去改产品，
而是先问：**到底是"产品没写"，还是"我没读到"？**

判据必须是**可以对上的外部事实**，最有用的是**PID**：

```
本次实战：
  测试第 5 段报：  "退出前 bridge pid=21660"
  产品日志里写：    "[bridge] 已启动 PID 21256" + "[exit] 收尾：已结束桥接进程 PID 21256"
  → 对不上 = 测试看的根本不是这个实例 → 问题在测试，产品没坏
```

**PID 对不上就直接停手。** 这一条如果早点用，那一个多小时能省掉。

## 规则 2：改产品之前，先在**完全隔离**的环境里复现；复现不出来就不许改

"完全隔离"的具体含义（缺一条都不算）：

1. 先把**所有**可能干扰的东西收干净：`presage-pet` 进程、监听 8792 的 node、
   `notepad`；然后**等 3 秒以上**让 TIME_WAIT 过去；
2. 用一个**全新解压**的副本（不是跑了一半的旧目录）；
3. **只跑一次**。反复连续跑同一套件会互相污染 —— 本次就是这个：
   我连续跑了 5 轮，还中途 `Stop-Process` 打断过一次，留下的 TIME_WAIT 8792
   和上一轮的 node 让 `Get-BridgeProcs` 张冠李戴。

**如果隔离环境下复现不出来 → 结论是"测试环境问题"，到此为止**，
不许改成产品代码。本次三次隔离复现是 3/3 通过，本该立刻收手。

## 规则 3：断言不许依赖"另一个进程还活着/对话框还在"这种不稳定状态

本次被这个咬了两次，都是同一个毛病：

| 曾经的写法（不稳定） | 为什么坏 | 改成 |
|---|---|---|
| "第二次双击后**进程数==2 且第二实例仍活着**" | 隐含假设"提示框一定挂在那儿等人点确定"；它可能被环境收掉 → 假红 | 数日志里 `[boot] 普瑞塞斯桌宠` 出现了几次：从 1 变 2 证明"它确实跑起来了"，再断言它走了「已有实例」分支 |
| "在**最后 400 行**里找某条日志" | 她一直在打 `[cursor-out]`/`[hitmask]`，检查点又晚 30 秒 → 那行被挤出窗口 → 假红 | 断言默认**读整篇日志**（`LogHas` 的 `$n` 默认 0 = 全文） |

两条通用化：

* **判据要挑"由被测对象写下来的、单调增长的东西"**（日志条数、`boot` 行数），
  而不是"某个进程此刻在不在"。
* **日志断言不要用尾部窗口**，除非你明确知道窗口足够大。窗口太小造成的红，
  **比不测更糟**：它会让人去改本来没坏的代码。

## 规则 4：断言失败的信息里必须能看出"它当时看到了什么"

本次那条红的原始信息是「整篇日志没有这行」——这句话本身就是**假的**
（它只是在那 28 行里没找到），而我当时信了它，才去追产品。

所以：**失败信息要带上原始证据**。本次改成的样子：

```powershell
Check '日志有「[bridge] 就绪」' ($bridgeReady.Count -ge 1) `
  $(if ($bridgeReady.Count) { $bridgeReady[-1] } else {
      '整篇日志没有这行；[bridge] 行 = ' + (@($allLines | Where-Object { $_ -match '\[bridge\]' }) -join ' || ') })
```

失败时它会直接把**所有 `[bridge]` 行**打出来。有了这个，一眼就能看出
"到底是没写、还是我没读到" —— 也就不需要再去加产品侧的留痕了。

> 这条还有个反面教训：**不要用"给产品加日志"来解决"测试读不到"的问题。**
> 本次我加的逐次轮询留痕本身是个无害的小改进（桥接起不来时能说清卡在哪一步），
> 但它**不解决**当时那个问题——问题在读取侧。加错了地方 = 白干 + 让交付物与源码失配。

## 附：本次真正值得留下的技术结论（与上面无关，是真发现）

| 发现 | 结论 |
|---|---|
| `Start-Process -PassThru` 在 DSH 会话里会**永久挂住** | 脚本一律用 `[System.Diagnostics.Process]::Start` |
| 用 `RedirectStandardOutput/Error` 起桌宠，**它 spawn 的 node 会继承那些句柄** | node 活着时父侧的读取/清理会一直等。给 GUI 常驻进程做自动化时，少用重定向，或者用完显式 `Kill()` 父进程 |
| `ProgramFiles` 环境变量**无法被子进程覆盖** | cmd 探针实测：`$env:` 与 `EnvironmentVariables[]` 两种写法（含 `_NEW`）都不生效，Windows 会用机器真实值填回去。所以"模拟一台没有 node 的机器"只能靠应用自己的开关（`PRESAGE_NODE=none`） |
| PowerShell 5.1 读**无 BOM** 的 `.ps1` 按 GBK 解码 | 中文注释直接让脚本在**解析阶段**崩，且**脚本内部的自我修复代码来不及执行**。所以带中文的 `.ps1` 必须 UTF-8 with BOM；丢了就跑 `tools\fix_ps1_bom.ps1`（纯 ASCII） |
| `tauri::Context` **不是 `Clone`** | 要重试 `build()` 就把 `tauri::generate_context!()` 放进循环里（资源是编进二进制的静态数据，没有运行时开销） |
